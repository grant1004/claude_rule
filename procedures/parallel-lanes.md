# 多問題平行處理（平行車道）

同一個專案同時處理多個問題時的做法。核心規則照常適用，尤其是第 5 節的 `WIP.md` 和待決事項。我沒有指定模式時用模式一。

## 啟動與中途加入

- 一般啟動：我說「平行處理」，並列出問題、建置指令、全套測試指令。沒給指令就從專案的 CLAUDE.md 找，找不到再問。
- 自動連續做：我用 `/goal` 啟動，條件以 `WIP.md` 為準。範本：
  `/goal 照平行車道流程處理下列問題和之後加進 WIP.md 的問題，直到 WIP.md 裡每個問題都是「已合併到 integration 且合併後全套測試通過」「受阻」或「略過」，而且最後一次回報列出了 WIP.md 的完整內容和最後一次全套測試的輸出。不可以刪除或放寬測試，不可以 push，不可以動 integration 以外的既有分支。最多 60 回合。問題：1. <問題一> 2. <問題二>`
- 執行中我又給新問題：先記進 `WIP.md`，和進行中的車道比對檔案與行為相依。重疊的排到那條車道後面，不重疊的開新車道。
- 你是協調者時不寫程式。我直接叫你改程式，就把它當成新問題走分診，不要自己動手。

## 共通

- 整合分支叫 `integration`，不存在就從目前的分支建立。只有協調者能動它。
- 不 push，也不動 `integration` 以外的既有分支，除非我要求。
- 開工前把 `WIP.md` 和 `.claude/worktrees/` 加進 `.git/info/exclude`，已經有就略過。

## 分診與分組（協調者，兩種模式共用）

1. 分診：把我給的問題整理成問題地圖，列出每題的疑似根因、會改到的檔案、彼此的關係。同根因的合併成一題。這一步只讀不改。
2. 分組：按會改到的檔案分車道。檔案重疊或屬於同一個模組的問題放進同一條車道，在車道內依序處理。會動到共用介面或資料格式的變更排在最前面，單獨做完再開其他車道。
3. 查行為相依：某條車道要改的檔案，被另一條車道的檔案呼叫或引用時，在兩張車道卡上互相註明，並讓其中一條先完成再開另一條。檔案不重疊不代表行為不互相影響。
4. 每條車道寫一張車道卡：車道名稱、負責的問題、可以改的路徑、不要動的路徑（其他車道持有的）、依賴的前提、重現方式、驗收條件、建置與全套測試的指令。
5. 把問題地圖和車道卡寫進 `WIP.md` 並列給我看。我開工時說過要先確認，就等我確認；沒說就直接開車道。標成「略過」的問題不派。

## 模式一：協調者加子代理車道

1. 每條車道派一個子代理，指定 worktree 隔離；互不相依的車道同時派出。派工單要能獨立看懂，內容是整張車道卡、下面「車道規則」的全文、核心規則第 5 節的不可逆判準、回報格式。
2. 車道之間不互相聯絡，一律經過你。
3. 車道回報「就緒」後先查證三件事：回報裡有全套測試通過的輸出和逐條驗收條件的結果；`git merge-base --is-ancestor integration <分支>` 成立；`git diff --name-only integration...<分支>` 列出的檔案都在車道卡可以改的路徑內。任何一項不成立，就恢復（resume）那個子代理要它補做，不要自己動手修。
4. 一次只合併一條：`git merge --no-ff <分支>`，只合併到本地的 `integration`。
5. 每次合併後更新 `WIP.md`，並恢復其他還沒合併的車道子代理，告訴它們落地了哪些檔案、行為有什麼變化，要它們 rebase 並重驗。
6. 車道回報受阻、派工有問題或有待決事項時，記進 `WIP.md`。派工有問題要先處理完，才能再派新的工作；其他車道照常進行。
7. 子代理中斷或沒有回報時重新派工：說明前一個執行者中斷了，附上完整的車道卡和已經存在的分支名稱。
8. 全部結束時照核心規則第 7 節回報，另外列出每個問題的結果、每條分支的名稱、`WIP.md` 的完整內容、最後一次全套測試的輸出。

## 模式二：每條車道一個獨立 session

1. 協調者用 `git worktree add ..\<專案>-<車道> -b fix/<車道>` 幫每條車道建 worktree，把車道卡給我，由我在各個 worktree 開 session。
2. session 之間只傳三種訊息：「就緒」「已落地」「需要動到車道外的檔案」。訊息發不出去，就把內容給我，由我轉達。
3. 車道先 commit 再發訊息。協調者沒收到「就緒」時，用 `git log integration..<分支>` 查看車道分支的進度，不要只等訊息。
4. 協調者收到「就緒」後，查證和合併的做法同模式一的第 3、4 步，合併前先問我；合併後向其他車道發「已落地」。

## 車道規則（子代理和獨立 session 都適用）

1. 開工先執行 `git rebase integration`，確保從整合分支的最新位置開始。
2. 只在自己的 worktree 裡、車道卡可以改的路徑內改檔，不碰「不要動」的路徑。需要動到範圍外的檔案，停下來回報，不要自己改。
3. 先重現問題。重現不出來就停下回報，不要硬改；它可能已經被別的車道修掉了。
4. 每完成一個可以驗證的小步，跑對應的測試，通過就 commit 到自己的分支。
5. 發現派工本身有問題（描述和程式碼矛盾、有派工時沒看到的相依、和略過的項目衝突）：立刻停止改檔，回報證據（`檔案:行號` 或 commit）和建議方向（延後、改範圍、改做法、交給我決定）。不要繞過問題繼續寫。
6. 遇到岔路要選，照不可逆判準判斷：可逆的照預設做，並在回報裡列出；不可逆的停下那個問題並回報。
7. 收到「已落地」：在下一個安全點（目前的小步已 commit、工作目錄乾淨）執行 `git rebase integration`，然後重跑重現與驗收。落地清單裡有你依賴的檔案，就重讀它再繼續。
8. 完成時依序執行：`git tag -f pre-rebase-<車道名稱>`、`git rebase integration`、全套測試、`git diff --name-only integration...HEAD`（確認只動到車道卡可以改的路徑）。全部通過才回報「就緒」，附上分支名稱、最後一個 commit、改了哪些檔案、行為有什麼變化、逐條驗收條件的結果（達成、部分、未達成）、全套測試通過的那段輸出、這次自動採用和還沒裁決的決定。
9. 全套失敗時：只重跑失敗的測試一次，分辨是不是偶發。穩定失敗就切到 `pre-rebase-<車道名稱>` 的位置跑同一個測試：那裡也失敗，是你自己改壞的；那裡通過，是和已落地的變更衝突。修好後從第 8 步重來。
10. 同一個失敗修了兩次還沒解決，就停下回報已知事實和試過的做法。
11. 不再往下派子代理。

## 收尾

全部問題都處理完之後才做，而且每一步都要我確認：

1. 併回正式分支：切到原本的分支，執行 `git merge --no-ff integration`。這是整個流程裡唯一會動到正式分支的地方。
2. 清理：先 `git worktree remove <worktree 路徑>`，再 `git branch -d <車道分支>`，最後 `git branch -d integration`。分支還被 worktree 使用時刪不掉，所以順序不能反。
3. 用 `git worktree list` 確認沒有殘留的 worktree。
