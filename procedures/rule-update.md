# 規則增修

規則的每一行都要用實際發生的問題換來，不預先想像。常駐的核心規則每個 session 都佔 context，規則越多，每一條被遵守的機會越低。

## 什麼時候提議

- 同一個錯誤出現第二次。
- 我糾正了一件從程式碼看不出來的事。
- 一個花了力氣才試出來的指令或做法。
- 你照某條規則做反而變差，或兩條規則互相衝突、已經過時。刪規則和加規則一樣重要。

## 不寫成規則的

- 你本來就做得對的事。
- 一次性的任務細節。
- 讀程式碼就知道的事。
- 能用工具強制的事。改為提議 formatter、linter、hook 或 CI 檢查。

## 放哪裡

| 規則的性質 | 位置 |
|---|---|
| 只和這個專案有關 | 專案的 `CLAUDE.md`（指令、驗證對照表、已知地雷） |
| 只和專案裡某些路徑有關 | 專案的 `.claude/rules/<主題>.md`，開頭用 `paths:` 指定範圍 |
| 每個專案、每個 session 都用得到 | claude_rule 的 `rules/core.md`，上限 80 行；超過就先刪或合併 |
| 特定情況才用得到的流程 | claude_rule 的 `procedures/` 下對應的檔案 |

## 怎麼提

- 格式：一條一行，「情境 → 做法（原因）」。
- 你只提議，不自己改規則檔：在完成回報裡寫出規則文字和建議位置，由我決定。
- 我說「回顧規則」時：列出這個 session 裡規則沒被遵守、規則造成多餘動作、以及缺規則而出錯的地方，各附一條具體的修改建議。

## 改 claude_rule 本身

- 改了 `rules/core.md` 就同時更新它「規則版本」那一行和 `VERSION` 檔，兩處要一致。
- 流程檔只改內容不必升版，但 commit 訊息要寫清楚改了什麼、因為哪件事。
- 改完之後，每台電腦要照 README 的「更新」重跑一次，新版才會生效。
