# 派工給子代理

子代理有三種用處：把大量閱讀隔離在主對話之外、平行處理互不相依的工作、提供沒看過實作過程的獨立檢查。代價是它從零開始、另外消耗用量，回報還會佔主對話的空間。所以預設自己做，符合下表才派：

| 情況 | 做法 |
|---|---|
| 要讀十個以上檔案才答得出來（追流程、找用法、讀 log、查文件） | 派唯讀的探索代理，只帶回結論和 `檔案:行號`。 |
| 三件以上互不相依、不碰同一批檔案的工作 | 平行派出，每個代理有明確的檔案邊界。 |
| 輸出很長的操作（全套測試、建置 log） | 派出去跑，只回報失敗項目和錯誤訊息。 |
| 需要目前對話的脈絡才做得了的支線工作 | 用繼承對話的 fork，不重新交代背景；沒有 fork 就自己做。 |
| L 級或高風險的變更完成之後 | 派全新 context 的審查代理，只給 diff 和驗收條件。 |

不派工的情況：S 級任務；步驟前後相依；會有兩個代理改同一個檔案；需要和我來回討論。

## 派工單

子代理看不到這段對話，派工單要能獨立看懂：

- 目標與用途：要回答什麼或完成什麼，結果會拿去做什麼。
- 範圍：可以讀、可以改哪些路徑；哪些不准碰。
- 已知事實：已經查過、排除過的事，避免重查。
- 完成條件，以及它必須自己跑的檢查。
- 回報格式：結論放最前面；每個主張附 `檔案:行號` 或指令輸出；標明哪些已驗證、哪些是推測；列出沒做完的部分；限制篇幅。

## 其他規則

- 同一個檔案同一時間只有一個代理寫入。要平行寫入就各用獨立的 worktree，由主對話整合。
- 搜尋、整理、跑測試這類機械性工作指定較小較快的模型；設計、難纏的除錯、審查用最強的模型。
- 子代理不再往下派工，除非派工單明確允許。
- 採用子代理的回報之前，抽查關鍵的 `檔案:行號`。宣告完成前的最後一次驗證，由主對話自己跑或親眼看過輸出。
- 審查代理只回報影響正確性或需求的缺口，不報風格偏好。它的每個發現都要判斷後再處理，不照單全收。
