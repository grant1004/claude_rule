# 調度：派工、驗收、落地

主對話是調度者，執行者是背景子代理：`cr-worker` 在工作目錄就地做，`cr-worker-isolated` 在自己的 git worktree 裡做。這份流程說明一個修改任務從進來到落地怎麼走，以及其他子代理的用法。

## 開工前

這個 session 第一次派修改任務時做一次：

1. 用 `git status` 和 `git branch --show-current` 看目前的分支和未 commit 的修改。目前的分支就是「落地分支」，所有任務的結果都 commit 或合併到這裡。
2. `WIP.md` 不存在就建立，記下落地分支和它現在的 commit（起點，之後要整批撤回時用）。格式見下一段。已經存在就接著用；格式不同時保留原有內容，補上缺的欄位。
3. 把 `WIP.md` 和 `.claude/worktrees/` 加進 git 的排除檔（位置用 `git rev-parse --git-path info/exclude` 查），已經有就略過。
4. 不 push，也不動落地分支以外的既有分支，除非我要求。
5. 下列情況不開 worktree，一律派 `cr-worker`、一次一個、其餘排隊：不是 git repo；專案的 CLAUDE.md 不准自動 commit（派工單要寫「不要 commit」）；專案的 CLAUDE.md 註明不能用 worktree。

## `WIP.md` 的格式

    落地分支：<名稱>　起點：<commit>

    | 代號 | 目標 | 可以改的路徑 | 狀態 | 由誰在哪裡做 | 等誰，或結果 |
    |---|---|---|---|---|---|
    | T1 | <一句話> | <路徑> | 進行中 | cr-worker，就地 | |
    | T2 | <一句話> | <路徑> | 排隊 | | 等 T1（都會改 <檔案>） |

    ## 待決事項

    - D1（T2）：<問題>。選項：<甲>／<乙>。建議：<甲>。

## 派工

- 選哪個執行者照核心規則第 1 節的表。派 `cr-worker-isolated` 之前多確認一件事：這個任務要讀或要改的檔案，在工作目錄沒有未 commit 的修改，因為它的 worktree 看不到未 commit 的內容。不符合就排隊。
- 找不到這兩個執行者時，告訴我執行者沒有安裝，改派一般的子代理，並把 `~/.claude/claude_rule/agents/` 下對應檔案的全文附在派工單裡。
- 執行者看不到這段對話，派工單要能獨立看懂：
  - 任務代號（`T<編號>`）和目標：要完成什麼，結果會拿去做什麼。
  - 範圍：可以改哪些路徑；哪些不准碰（其他任務持有的）。
  - 已知事實：查過和排除過的事、重現方式。
  - 完成條件，以及必須跑的檢查。
  - 落地分支的名稱和它現在的 commit。
  - 要不要 commit（預設要）。
- 派出後更新 `WIP.md`（連同執行者的 agent ID，之後要叫它回來時用），用一兩行告訴我，然後結束回合。不等待，不輪詢。我問進度時照 `WIP.md` 回答，還在跑就說還在跑。
- 我問進度而執行者已經不在跑、也沒有回報時：先用 `git log` 和 `git status` 看實際進度，再重新派工，說明前一個執行者中斷了，附上原本的派工單和已經存在的分支。

## 完成通知進來時

先把下面的事做完，最後才回報：

1. 驗收。回報是待查證的主張：用 `git show --stat <commit>`（隔離執行者用 `git diff --stat <落地分支>...cr/<任務代號>`）確認改動都在派工單的範圍內；確認回報裡有實際跑過的指令和結果，沒跑的有寫原因。有疑點就抽查 `檔案:行號`。同一份程式碼已經通過的檢查不重跑。不合格就用 SendMessage 把同一個執行者叫回來補做，不要自己動手修。
2. 落地。
   - `cr-worker`：它已經 commit 在落地分支上，驗收通過就算落地。
   - `cr-worker-isolated`：工作目錄沒有執行者在用時才合併。先確認 `git merge-base --is-ancestor <落地分支> cr/<任務代號>` 成立，代表它驗證過的內容就是合併後的內容；成立就執行 `git merge --no-ff cr/<任務代號>`。不成立，或合併出現衝突（先 `git merge --abort`），就用 SendMessage 告訴它落地分支前進了，要它 rebase 並重驗。叫不回來就把任務改成排隊，之後派 `cr-worker` 就地重做，派工單附上分支名稱。
   - 合併後清理：`git worktree remove <worktree 路徑>`、`git branch -d cr/<任務代號>`、`git branch -d <worktree 原本的分支>`、`git tag -d pre-rebase-<任務代號>`（有才刪）。移除失敗時不要加 `--force` 或 `-D`，列給我決定。
3. 執行者回報「受阻」或「派工有誤」：記進 `WIP.md`。派工有誤就修正派工單再重派。原因是 worktree 的環境建不起來時，把任務改成排隊就地做，並在回報裡建議把原因寫進專案 CLAUDE.md 的 Git 段。
4. 更新 `WIP.md`，再派出原本在等這個任務的排隊項目。派出前對照剛落地的改動重新確認前提，前提變了就重寫派工單。
5. 照核心規則第 8 節回報。

## 其他子代理

修改以外的工作，符合下表才派，否則主對話自己做：

| 情況 | 做法 |
|---|---|
| 要讀十個以上檔案才答得出來（追流程、找用法、讀 log、查文件） | 派唯讀的探索代理，只帶回結論和 `檔案:行號`。 |
| 輸出很長的操作（全套測試、建置 log） | 派出去跑，只回報失敗項目和錯誤訊息。 |
| 需要目前對話的脈絡才做得了的支線工作 | 用繼承對話的 fork，不重新交代背景。 |
| L 級或高風險的變更落地之後 | 派全新 context 的審查代理，只給 diff 和驗收條件。 |

- 搜尋、整理、跑測試這類機械性工作指定較小較快的模型；設計、難纏的除錯、審查用最強的模型。
- 採用子代理的回報之前，抽查關鍵的 `檔案:行號`。
- 審查代理只回報影響正確性或需求的缺口，不報風格偏好。它的每個發現都要判斷後再處理，不照單全收。

## 收尾

我說「收尾」，或所有任務都結束時：

1. 回報每個任務的結果、`git log <起點>..HEAD --oneline`、還沒處理的待決事項。
2. 用 `git worktree list` 和 `git branch --list "cr/*"` 檢查有沒有任務留下來的 worktree（`.claude/worktrees/` 底下的）和任務分支。有就列給我，由我決定要不要刪。我自己建的 worktree 不要動。
